# 根因分析：OpenHarmony x86_general（QEMU/virtio-gpu/swrast）截图全黑

> 2026-10-19 ~ 10-20 两轮排查的最终结论。供后续项目避坑与深挖参考。
> 排查全程证据见 evidence/ 与 logs/。

## 一句话结论

**GL/软渲客户端向 dumb-backed EGLSurface 输出的像素会整体丢失**（渲染调用链正常、缓冲正常流转，但最终内存里没有像素）；CPU 渲染路径（mmap 写）像素完好。系统里最重的 GL 客户端是 SystemUI——它走 GL 就是全黑，走 CPU 就是 6.5 万色锁屏。

## 因果链（时间序）

1. OHOS clang 对 musl 默认 `-femulated-tls` → mesa 的 emutls 地址表按副本隔离 → `glGetString` 恒 null → **修复**：mesa 10 库 `-fno-emulated-tls` 重编（已入镜像）
2. wrapper libEGL 的 `HiLogPrint` JUMP_SLOT 在 appspawn 沙箱懒解析失败 → GOT 保持初值 → 首调野跳 SEGV；BlobCache::WriteToDisk 同病 → **修复**：wrapper 内本地 T 符号 stub + BlobCache 四处短路（v4）
3. 该 bug 在「热环境」下表现为 SystemUI 崩溃环/挂起；在「冷启动」下表现为一次温和的 eglInitialize 失败 → ArkUI 自动 CPU 回退 → **这恰是 10-19 出现彩色锁屏的偶然原因**
4. 10-20 复现失败后定位到真正分层：EGL 成功（GL 路径）=黑；EGL 失败（CPU 路径）=彩色 → 在 wrapper 里加 marker 门控的 eglInitialize 强制失败（`/data/egl_no_init`），把偶然变成确定
5. 显示侧独立卡点（与截图无关但同期排查）：内核 virtio_gpu 主平面格式表缺 ARGB8888（EINVAL）→ 已补；composer HAL 从不设 SRC_*/CRTC_* 几何（scanout 0x0）→ 已补

## 已实证的机制（勿重复排查）

| 事实 | 证据 |
|------|------|
| GL 写入丢失：CPU mmap 与 QEMU 资源 iov 指向不同内存 | drmprobe 写梯度 + SetCrtc，QEMU trace 收到全部 transfer/scanout/flush 但画面不变；mapper mmap 读回却有内容 |
| `/dev/fb1` 的 write() 不标记 deferred-io damage | 内核 fb_io_write 源码纯 memcpy |
| fbcon 自身重绘是唯一能把 fb1 内容推上 QEMU 屏的机制 | console spam 滚动时 dd 的写入顺带上屏（22:18 实验） |
| composer plane commit 与 fbcon 重绘互相抢 plane | set_scanout 交替 + 覆盖实验 |
| QEMU screendump == virtio-gpu scanout 内容 | fb1 写 0 → 对应区域变黑 |
| snapshot_display 是 RS 内部渲染，不依赖 composer/DRM | composer 全停时快照依旧彩色 |
| 杀 render_service 不可恢复（vsync/会话链断裂），冷启动可恢复 | 多轮实验 |

## 遗留深坑（未解，按优先级）

1. **iov 页分裂**（用户态 dumb buffer 的 sgt/QEMU iov 与 mmap 页不一致）：修复后可 rm `/data/egl_no_init` 恢复 GL 全速路径，硬件屏也有望直接通
2. **硬件屏显示**：mirror→fb1→console-poke 旁路已写入 HAL（marker `/data/hdi_mirror` 启用，曾验证 91% 像素上屏），被 RS present 生命周期停摆（boot 后一段时间停止出帧）卡住
3. RS 与 composer 的会话生命周期：composer 死亡后 RS 重握手不完整（vsync worker 不重启 / present 停摆）
